# OpenLiero Web Port Plan

Last updated 2026-11-11.

## Goal and strategy

The goal is OpenLiero running in the browser, with tctool still available as a command-line converter. We get there in three phases, and each phase ends with a working build:

1. **Emscripten build of the existing C++ code.** No rewrite, just build changes and a few `#ifdef __EMSCRIPTEN__` blocks. This build becomes the reference that later phases are checked against.
2. **Gradual port to Rust inside the same Emscripten build.** Game logic moves first, one module at a time, with replays used to confirm nothing changed.
3. **Pure Rust on `wasm32-unknown-unknown`.** Once no C++ is left, Emscripten is dropped.

A fourth phase then cleans up the Rust the port left behind: no `unsafe`, and idiomatic code.

tctool runs alongside all three phases as a Rust command-line tool in `tools/tctool`. Its reading and writing are in the `rust/liero-data` crate, which the game also loads TCs with; later the same reader becomes the importer inside the browser game.

## Current architecture

The codebase is about 70,000 lines of C++11 and C. SDL2 and SDL2\_image are its only system libraries, and zlib/miniz is bundled. The main loop, the threads and file access are what need work; graphics and game logic port as they are.

| Area | Current code | In the browser |
| --- | --- | --- |
| Rendering | 8-bit software renderer, presented through `SDL_Renderer` (`Gfx::draw`, `gfx.cpp`) | Works with Emscripten's SDL2 |
| Main loop | Blocking `do { process(); flip(); } while(true)` loops in every menu and in the game; `flip()` waits with `SDL_Delay` | **Main blocker**: the page can't block |
| Input | `SDL_PollEvent` / `SDL_WaitEvent`, scancodes | Works; some keys are taken by the browser |
| Audio | `SDL_OpenAudio` with a callback mixer (`sfx.cpp`) | Works after a user click or keypress |
| AI | `WorkQueue` with `SDL_CreateThread` and mutexes (`ai/work_queue.hpp`), but only under `AI_THREADS`, which is off | Already single-threaded |
| Files | `opendir` / `FindFirstFile` in `filesystem.cpp`; settings and replays saved to disk | Needs a virtual file system and persistent storage |
| Data | `TC/openliero`: about 100 `.cfg`, `.tga` and `.wav` files | Easy to bundle |
| tctool | 1,200 lines in `src/tc_tool`; reads `LIERO.EXE`, `LIERO.CHR` and `LIERO.SND`, writes a TC folder | Command-line file tool, no SDL window |

## Phase 1: Emscripten build of the C++ code

Phase 1 is done when local 2-player games, menus, sound and saved settings all work in the browser, built from the same sources as the desktop version.

**Toolchain.** The repo's `docker-compose.yml` provides both toolchains in Docker, so nothing else needs installing: `native` (Alpine 3.22 and Cargo) and `web` (Debian trixie with emsdk 4.0.0 and Bun 1.4.4; emsdk's prebuilt tools need glibc, so not Alpine).

- [x] **Build target.** An `if(EMSCRIPTEN)` branch in `CMakeLists.txt` links Emscripten's SDL2 ports (`-sUSE_SDL=2 -sUSE_SDL_IMAGE=2 -sSDL2_IMAGE_FORMATS=tga,png`) and builds only `openliero`, as `build/web/openliero.html`, `.js` and `.wasm`. `gvl` and `tl` now recognise wasm32 as a little-endian architecture. The build links but doesn't run yet: it needs the main loop and game data steps below.
- [x] **Main loop.** Linked with `-sASYNCIFY -sASYNCIFY_STACK_SIZE=65536` (the 4 KB default crashed at the first sleep). `Gfx::flip()` calls `emscripten_sleep` every frame, even when behind, because the browser only shows a frame once control returns to it. `SDL_WaitEvent` already yields, since SDL's `SDL_Delay` calls `emscripten_sleep` under ASYNCIFY. Menus, weapon select and 2-player games run. The build also needs `-fexceptions`, because the game reports errors with C++ exceptions. ASYNCIFY grew the `.wasm` from 1.3 MB to 1.9 MB. Phase 3's "Replacing the main loop" has since removed it.
- [x] **AI threads.** No change needed: `WorkQueue` was only used under `#if AI_THREADS`, which was never defined, so the predictive AI already ran on the main thread in every build (both are gone since the AI moved to Rust). A 2-player game against a CPU bot holds 60 fps in the browser (median frame 16.7 ms, worst 32 ms after the start-up spike). GitHub Pages' missing COOP/COEP headers don't matter while it stays that way.
- [x] **Game data.** Bundled with `--preload-file TC/openliero@/TC/openliero` (600 KB `.data`). The POSIX branch of `filesystem.cpp` (now also chosen for `__EMSCRIPTEN__`) works on Emscripten's file system. The bundled sounds were renamed to lower case to match `tc.cfg`, which also fixes them on case-sensitive Linux. CMake doesn't track the data files, so delete `build/web/openliero.*` to repackage after changing them.
- [x] **Saving.** Mount IDBFS on the folder for settings, profiles and replays. Load it with `FS.syncfs(true)` at startup and save with `FS.syncfs(false)` after each write. `web/shell.html` mounts IDBFS on `/liero` before the page offers to start and loads it, and the game uses it as its config folder (`--config-root /liero`), finding the preloaded TC with a new `--tc-root /TC`. IDBFS's `autoPersist` saves each file when the game closes it, and the page saves again when it is hidden or closed. The game only wrote liero.cfg when it quit, which a closed tab never does, so in the browser the menu writes it whenever the settings change. If IndexedDB fails, as in some private windows, `/liero` stays in memory and the game runs without saving. A replay still being recorded when the tab closes is lost, since the game keeps it in memory until the match ends.
- [x] **Browser details.** Add a click-to-start screen so audio can start, call `preventDefault` on the game's keys, give player 2 default keys that exist on Mac keyboards (there is no Right Ctrl, and Ctrl+arrows switch Spaces), make the canvas fill the window, and turn off the spectator window.
- [x] **Hosting.** Publish a static page (`index.html`, `.js`, `.wasm`, `.data`) on GitHub Pages, built and deployed by a GitHub Actions workflow on every published release: <https://lmajamaa.github.io/rusty-liero/>. Bun is the web runtime: `web/serve.ts` (Bun.serve) serves the build locally with the right MIME types and no COOP/COEP headers, matching what Pages serves.

**Done since:** every menu and the game is now a screen with a `tick`, run from `emscripten_set_main_loop`, and ASYNCIFY is gone (Phase 3, "Replacing the main loop").

## tctool as a command-line utility

tctool is rewritten in Rust as a standalone command-line tool (`tools/tctool`, crate `liero-tctool`, binary `tctool`). It depends only on `rust/liero-data`, takes the same arguments as the C++ tool did and writes byte-identical output. The C++ tctool (`src/tc_tool`) is removed.

| Form | How it's built | How it's run |
| --- | --- | --- |
| Rust CLI | `cargo build --release` in `tools/tctool`, locally or in the `native` Docker image | `tctool [--tc-name NAME] [--config-root DIR] <liero-dir>` |
| Browser importer (later) | The Rust reader compiled to wasm with the game | Drop `LIERO.EXE`, `LIERO.CHR` and `LIERO.SND` on the page |

Remaining steps:

- [x] **Compile and fix.** Builds cleanly in the `native` image (no fixes needed).
- [x] **Compare outputs.** The 1.36 bundle wasn't at hand, so the comparison used Liero 1.33's LIERO.EXE, LIERO.CHR and LIERO.SND (the 1.36 bundle's README steps name its conversion "Liero v1.33" too). Both tools wrote the same 113 files, byte for byte. They were also compared on a generated installation of random bytes, which reaches every field over its whole range. That found two bugs in the C++, none in the Rust: `font.tga` was written for as many pixels as a character's width byte said, so a width over 7 wrote past the glyph (and, for the last characters, past the buffer), and a reference to an object past the last one (`splinterType`, `createOnExp` and the like) was looked up without a bounds check. Both crashed the C++ tctool. The Rust writer clips the width to 7 and writes such a reference as `null`; Liero 1.33 has neither case. With those two checks added to the C++ for the test, the outputs were identical.
- [x] **Remove the C++ tctool.** `src/tc_tool` and its CMake target are gone; the game sources it compiled are still used by the game, and `common_model.hpp` by `hashtc.cpp`. `docker compose run --rm native` now builds the Rust tctool. The native CMake build only defines `videotool`, which already didn't build: it needs `ffmpeg/` and `x264/`, which aren't in the repository, and the Rust library, which is only built for the web.
- [x] **Test in CI.** `tools/tctool/tests/convert.rs` runs the tctool binary and compares the TC folder with a listing in `sha256sum` format (`sha256sum -c` checks one too). The original files can't be in the repository, so CI converts a generated installation: LIERO.EXE and LIERO.CHR of seeded random bytes, apart from distinct weapon names, and a LIERO.SND with 30 sounds of noise, some empty (`tests/synthetic.sha256`). With `LIERO_133_DIR` set, it also checks the Liero 1.33 conversion against `tests/liero133.sha256`. Both listings were checked against the C++ tctool's output before it was removed. `TCTOOL_UPDATE_LISTINGS=1` rewrites them after an intended change.

## Graphics in the browser

Rendering needs almost no changes. The game draws each frame on the CPU, and SDL only uploads the finished frame and shows it, which Emscripten's SDL2 does with WebGL.

| Step | Current code | In the browser |
| --- | --- | --- |
| 1. Draw | Game writes into an 8-bit palette bitmap, 320×200 or 640×400 | Unchanged, runs as WebAssembly |
| 2. Convert | `scaleDraw` turns it into 32-bit ARGB using the palette, scaled by a whole number | Unchanged, runs as WebAssembly |
| 3. Upload | `SDL_UpdateTexture` | Uploads into a WebGL texture (`texSubImage2D`) |
| 4. Show | `SDL_RenderCopy`, `SDL_RenderPresent` | One textured rectangle drawn on the `<canvas>`; the browser shows it when control returns |

Changes needed:

- **Spectator window:** the browser has one canvas, so turn it off in the web build.
- **Scaling filter:** `SDL_HINT_RENDER_SCALE_QUALITY` is `"linear"`, which blurs pixel art. Use `"nearest"`, or CSS `image-rendering: pixelated`.
- **Canvas size:** resize the canvas to the window; `fitScreen` and `SDL_RenderSetLogicalSize` handle the rest.
- **Frame timing:** the game ticks every 14 ms (about 70 Hz) and most screens refresh at 60 Hz. Use a fixed-step loop that runs as many 14 ms ticks as real time requires and draws once per refresh. This also keeps game speed exact for replays.

Optional: move the palette conversion into a WebGL shader. It isn't needed for performance.

## Phase 2: gradual Rust port inside the Emscripten build

Rust code is built as a static library for `wasm32-unknown-emscripten`, and `emcc` links it with the remaining C++ into one `.wasm`. Every step is checked against replays, so the game stays playable throughout.

**How the two sides connect**

- Plain C functions (`extern "C"`, `#[no_mangle]`) with simple types and `#[repr(C)]` structs. `cbindgen` generates the C header.
- C++ holds an opaque handle to state owned by Rust, or whole subsystems move across at once. Rust can't use C++ classes like `Game` or `Worm` directly.
- Rust's `std::fs` works on Emscripten's file system, so the preloaded TC data and the IDBFS saves are readable from Rust too.
- Build with `panic = "abort"` and never let a panic cross into C++.
- Keep the `rustc` and `emcc` LLVM versions close to avoid link errors.

**The bridge** (in place):

- [x] `rust/liero-game` is a `staticlib` crate (`liero_game`). CMake runs `cargo build --release --target wasm32-unknown-emscripten` for it on every web build, into `build/web/rust`, and links it into `openliero`.
- [x] The C header `rust/liero-game/include/liero_game.h` is generated by cbindgen and checked in.
- [x] Pinned versions: Rust 1.87.0 (LLVM 20.1) in the `web` image, matching emsdk 4.0.0's clang 20. Alpine 3.22's `cargo` is also 1.87.0. Change Rust and emsdk together. Since emsdk went, Rust is 1.100.0 in both images (Alpine's `native` installs it with rustup too) and in CI, which also builds the `wasm-bindgen` CLI with it.
- [x] Smoke test: `liero_game_version()` is called from `main.cpp`, which prints `liero-game 0.1.0` at startup in the browser.
- [x] Decided: the game is only built for wasm. The native CMake build now makes only the command-line tools (`tctool`, and `videotool` on request). Files only the desktop game used are removed: the macOS bundle and Windows icon files, `pkg/`, `CMakeSettings.json`, and about 200 sources and headers no target builds, mostly unused parts of `src/tl` and the original zlib (`miniz.c` replaces it).
- [x] CI (`.github/workflows/test.yml`, on pushes to main and on pull requests) runs the Rust tests natively and as wasm, checks the header against cbindgen's output, builds the game, checks game-state hashes (below), builds tctool, checks its output against a listing and runs the `liero-data` tests.

**Porting order**, starting with code that depends on nothing else:

1. [x] `math`, `rand`, fixed-point helpers: in `rust/liero-game/src/{rand,math}.rs`. C++'s `Rand` is now a thin wrapper that inherits the Rust state struct (`LieroRand`, the `gvl::mwc` multiply-with-carry generator, not CMWC), so games still copy and archive it as a plain value. `vectorLength` and the cos/sin table call Rust. Tests compare long output streams with hashes printed by `rust/liero-game/reference/reference_values.cpp`, which runs the original C++ code through em++. They pass natively and as wasm. Two findings: the cos/sin table relies on signed 64-bit overflow wrapping around, and native g++ on arm64 only matches wasm with `-ffp-contract=off` (no fused multiply-add).
2. [x] `level` and materials: in `rust/liero-game/src/{level,material}.rs`. Random level generation, shadows, Holdazone spawn selection, the miniature and the terrain operations from `blit.cpp` (stones, dirt effects, images drawn on the map, shadow correction) are in Rust. C++'s `Level` still owns its pixels and materials as vectors, so games copy and swap levels as before, and passes Rust a `LieroLevel` view plus a `LieroLevelCommon` view of the TC's materials, textures and large sprites. `Material` inherits Rust's `LieroMaterial` but keeps its flag tests inline, because the renderer and AI call them for every pixel. Tests run the original code in `reference_values.cpp` on made-up TC tables and compare random levels, 3,000 random terrain operations, spawn selection and miniatures. In the browser, a CPU-vs-CPU game with fixed seeds gave the same level, material and rand hashes as the `main` build for 2,800 ticks.
3. [x] Object physics: in `rust/liero-game/src/object.rs`. Blood particles (`bobject`), bonus boxes falling and bouncing, explosion animation (`sobject`) and the push explosions give worms and objects are plain Rust functions. Non-weapon objects (`nobject`: shrapnel, dirt, blood, bomblets) and the ninja rope run in Rust with a table of C++ hooks for what stays in C++: creating other objects, hitting and hurting worms, sounds and stats. C++ still owns the objects in their fixed arrays, so Rust gets pointers to an object's fields and reads and writes them where the C++ did: a hook may push or reuse the object being processed. `BObject` and `Ninjarope` are used in place, with `static_assert`s on their layout. Unit tests cover the explosion maths; the game-state hashes below cover the rest, with every ported branch reached by the bot games.
4. [x] Weapons: in `rust/liero-game/src/weapon.rs`. Firing (`Worm::fire`: ammo, fire cone, shells, spread and recoil), the start of each shot (`Weapon::fire`: velocity, first frame, fuse), reloading (`Worm::processWeapons`) and weapon objects (`WObject::process` and `blowUpObject`: steering, bouncing, trails, pushing other objects, lasers, exploding) are in Rust, with C++ hooks for creating objects, hitting worms, sounds and stats, as in step 3. `WormWeapon` is used in place. All 32 branches of the port run in the bot games except two this TC can't reach: no weapon stops on the ground without exploding, and the TC turns `SignedRecoil` off.
5. [x] Worms: in `rust/liero-game/src/worm.rs`. `Worm::process` and everything it calls are in Rust: terrain reaction forces, physics and bouncing, walking, digging, jumping, aiming, the rope controls, weapon changing, the laser sight, steering, bonus pickups, bleeding, dying (with the game-mode rules for lives, kills and 'it') and respawning. The respawn position check moved from `game.cpp` with it. C++ hooks cover the bonus and weapon object lists, healing, creating objects, sounds, the other worm and stats; firing and reloading call the step 4 functions directly. The bot `DumbLieroAI` stays in C++ with the controllers. A Scales of Justice game was added to the hash runs, and all but 7 of 59 counted branches run: fall damage and worm float are TC hacks this TC turns off, and the bots never reach the level's right and top edges or the rope's maximum length.
6. [x] The game tick: in `rust/liero-game/src/game.rs`. `Game::processFrame` runs in Rust in the original order, calling C++ hooks for each object list, each worm and rope, and the viewport and stats bookkeeping, which isn't game logic. The game rules around it are in Rust too: spawning bonuses, the Game of Tag and Holdazone timers and zone, damage and healing (including Scales of Justice moving health between worms) and the end of the game. `Holdazone` is used in place. Two games were added to the hash runs, Scales of Justice with guns and Holdazone with shotguns, and all but 5 of 29 counted branches run: the TC turns the bonus spawn rectangle off, the bonus list can't fill up, a new zone holder always has a contender, and the bots never make the zone shrink or a capture decay.
7. [x] TC data: the `rust/liero-data` crate, shared by the game and `liero-tctool`. It holds the model, tctool's LIERO.EXE/CHR/SND reader and TC folder writer (moved from `tools/tctool`), and a new TC folder reader, a port of `Common::load`: the game's TOML dialect (`gvl::toml::reader`, quirks included: no line break at the end of a file, the first of two keys wins, `\u00XX` read as a byte, integers wrap), the WAV and TGA readers with their silent fallbacks (another WAV format gives no sound, a TGA of the wrong size stays blank) and the font's width rule. `Common::precompute` (the weapon order and the worm and fire cone sprites facing both ways) moved to `rust/liero-game/src/tc.rs`. C++ reads each file for Rust through a hook, so a TC can still be a folder, a zip file or joined folders, and copies the result into `Common`. The hash run now hashes everything loaded: the TOML parts written back out with the C++ writer, and the sprites, palette, font, sounds and precomputed tables (112 lines). Tests read the bundled TC, write it back and read it again; with `LIERO_133_DIR` set, they also convert an original Liero 1.33 and check it reads back (it gives the bundled TC exactly, apart from the sounds, which came from another LIERO.SND). Two things the format can't hold: a font character 7 pixels wide reads back with width 0, as in the C++ (character 27), and the bundled TC's .cfg files have LF line breaks and some WAV files lack the padding byte, which the reader ignores. Moving the loading exposed a C++ bug: a health bonus's `weapon` was never initialized, so the hash read whatever the loader had left in that memory. `Bonus()` now sets it to 0; that changed 1,148 state hashes in 16 games and no frame hash or game result, since nothing else reads it, and the baseline was re-recorded from the C++ with that one fix.

The other, halving the sum of two samples with a shift rather than division, can't change anything: both samples are multiples of 30, so the sum is even. Unit tests (native and wasm) cover the mixer's timing, loops, ids, volumes, clipping, empty sounds and clock wrapping, the key table, key state, frame skip, joystick keys, key names and controls. ## Phase 3: pure Rust without Emscripten

Once no C++ is left, the web build moves to `wasm32-unknown-unknown` with `wasm-bindgen` and `trunk`, and native builds use the same code.

| Area | Web build | Native build |
| --- | --- | --- |
| Graphics | `pixels` crate (framebuffer on `wgpu` / WebGL2) | `winit` + `pixels` |
| Main loop | `tick()` called from `requestAnimationFrame`, fixed 14 ms steps | Same `tick()`, driven by `winit` |
| Files | TC data embedded with `include_bytes!` or fetched; saves in IndexedDB | `std::fs` |
| Audio | Web Audio through `cpal` or `kira` | `cpal` or `kira` |
| tctool | Browser importer calls `liero-data` | `liero-tctool` CLI calls `liero-data` |

**Replacing the main loop.** Today the game is nested C++ loops that never return to the browser: `Gfx::mainLoop` runs the main menu (`menuLoop`), menu items run their own loops, and the game runs inside the controller's. Each loop draws, then calls `Gfx::flip()`, which sleeps through `emscripten_sleep`; that only works with ASYNCIFY, which costs about 0.6 MB of wasm and some speed. Fourteen loops block that way: `mainLoop` and its game loop, `menuLoop` and its fade-out, the file selectors (`selectLevel`, `selectProfile`, `selectReplay`, `selectOptions`, `selectTc`), `weaponOptions`, `inputString` (also used for numbers), `infoBox`, `waitForKey`, `waitForKeyEx` (choosing a key) and the stats screen (`presentStats`). Not all of them show a frame every tick: the text box shows one per event, and the message box and key choice show one and then wait. The replacement is a stack of screens in Rust, one per loop, each with a `tick` that gets the frame's events, says whether it showed a frame, and stays, opens a screen on top, closes with a result for the screen below, or replaces itself. One frame function runs the top screen with fixed 14 ms steps, capped so a tab coming back from the background doesn't race to catch up, and later `requestAnimationFrame` or `winit` calls the same function. ## Phase 4: safe, idiomatic Rust

Phase 4 starts when phase 3 is done: no C++ is left and nothing calls the `liero_*` C functions. It is done when `liero-game` and `liero-data` build with `#![forbid(unsafe_code)]`, clippy is clean without the `#[allow(clippy::…)]` lines CI started with (raw-pointer accessors, boxes that raw pointers point into, and ported functions with many arguments), and `tools/hashrun/expected.txt` hasn't changed by a line. The Rust written in phase 2 was shaped by C++ on the other side: it is correct, but it reads like C.

**Where it stands** (2026-11-11, counted by `tools/rust-patterns/report.ts`; 27,896 lines of Rust):

| Pattern | Count | Why it's there | What replaces it |
| --- | --: | --- | --- |
| `unsafe` blocks / `unsafe fn` | 475 / 569 | Nearly all follow from the rows below | Nothing |
| `extern "C" fn`, `#[no_mangle]` | 579 / 364 | The C++ boundary and the hook tables | Plain functions and methods |
| Raw pointer types | 773 | Views of C++ memory, field pointers, `ctx: *mut c_void` (202 `c_void`) | `&`/`&mut`, slices, indexes |
| `#[repr(C)]` | 131 | Layouts shared with C++ | Plain structs and enums |
| `Box::into_raw` / `from_raw` | 85 | Boxes C++ held handles to | Owned fields |
| `slice::from_raw_parts` | 44 | Pointer-and-length views (`LieroLevel`, `LieroStr`, bitmaps) | Slices, `Vec`, `String` |
| `Rc<UnsafeCell<T>>`, `Shared<T>` | 10 | Reference counts shared with C++ | `Rc`, or one owner |
| `&'static mut` from a global | 5 | `app()`, the menus | An `App` passed by `&mut` |

All of it is in `liero-game`; `liero-data` and `liero-tctool` have no `unsafe` today. Other habits from the port: the `Liero` prefix on 151 structs and `liero_*` free functions where methods belong, `LIERO_*` integer constants where enums belong, structs with a `found` flag where `Option` belongs, about 1,000 integer `as` casts, 170 `for i in 0..n` loops, and two copies of the TC's model (`liero-data`'s and `liero-game`'s `repr(C)` one).

**Rules for every step**

- Behaviour doesn't change. The unit tests and the hash run (in Rust since phase 3, step 6) pass, the hash run natively and on the web build, with `expected.txt` untouched. A fix to behaviour (below) is its own PR, never mixed into a cleanup.
- One PR per step or sub-step, each checked with 5–10 bugs planted at its risky spots; a plant the hashes miss gets a unit test.
- The counts only go down. Once phase 4 starts, the `rust-patterns` workflow fails a PR that raises any row, and reports new rows for `c_void`, `from_raw_parts`, `Box::into_raw`/`from_raw`, `UnsafeCell` and `&'static mut`.
- Speed is measured, not assumed: the hash run's time and the browser's frame times with two predictive bots, before and after each step that touches a hot loop (drawing, the level, the AI playing copies of the game). Bounds checks and `RefCell` are the two things that could cost.

**Kept as it is, on purpose.** These look unidiomatic but are the game's behaviour, and the hashes hold them:

- `cpp_sort.rs`, the port of libc++'s `std::sort`, and the pairing heap in `ai/path.rs`: the order of ties decides what the stats screen shows and where a bot aims.
- Wrapping arithmetic and truncating casts in the physics, the cos/sin table and the mixer (most of the 234 `wrapping_*` calls). They get a newtype or a comment, not a change.
- The fixed object lists with their sentinel slot and slot reuse order, the TOML dialect's quirks, the mixer's channel id rules, and every finding listed under phase 2 as "kept".
- Large game state on the heap (`Box<GameData>`, 74 KB), which the AI's copies rely on.

**Afterwards, as behaviour changes.** Each needs its own PR and, where a hash moves, a re-recorded line with the reason: errors that panic because C++ never caught them (a replay's read error during playback, an out-of-range error while recording) become `Result`s that end in a message box; and `unwrap`/`expect` outside tests (about 160 with the tests') are audited the same way. `panic = "abort"` can stay for the wasm size.

**Risks**

| Risk | Effect | Fallback |
| --- | --- | --- |
| A safe rewrite of the tick reads a field at a different point than C++ did | Desyncs that only show in rare games | Index access at the same read points; plants at slot reuse; more seeds in the hash run for that step |
| Bounds checks or `RefCell` slow the AI or drawing | Bots slow the game on one thread | Measure per step; hoist slices out of loops; restructure ownership instead of reaching for `RefCell` |
| Step 7's ownership doesn't fit `Rc<RefCell<_>>` without runtime borrow panics | Panics in the menus or playback | Pass borrows down from `App` instead of sharing; settings snapshots per game |
| A crate chosen in phase 3 forces `unsafe` at its edge | `forbid` can't cover everything | The platform crate holds it, counted and commented |

## Write-up: how the port was done

1. [ ] **`RUST_PORT.md`**, the porting strategy as it was carried out, for someone porting another C++ codebase to Rust. Built from the merged pull requests: their descriptions, review comments and commits (`gh pr list --state merged`, `gh pr view --comments`), read in order. ## Later: online multiplayer

The game logic is deterministic and replays already record only inputs, which makes it a good fit for rollback netcode. Players send each other inputs over WebRTC DataChannels, and a small Bun server (Bun.serve with WebSockets) only connects them. GitHub Pages only serves static files, so that server needs a separate host. The old unused `src/tl/socket.c` has been removed; it couldn't run in a browser anyway.
